# CampusPulse

**Development of an ESP32-Based Real-Time Student Class Status Monitoring with Notification System
and GPS Tracking** — Antipolo City National Science and Technology High School (ACNSTHS).

Live app: **https://campuspulse-acnsths.vercel.app**

## How it works

1. Each student opens the web app and gets a **QR gate pass generated by the server**. Each code
   works for only **3 minutes**; the app then shows a new one by itself, so a screenshot or a code
   sent to a friend stops working.
2. The **ESP32-CAM gate scanner** at the classroom entrance reads it from the phone screen and sends
   it over Wi-Fi to the server.
3. The server checks that the code **exists, belongs to a student, is from today, is less than
   3 minutes old and has not been used for that entry**, then updates the class status: **On Campus**, **Late** (after the cut-off
   time), and on the second scan at dismissal, **Checked Out**. Anything else is rejected, which
   stops buddy check-ins and reuse of old codes.
4. Every valid scan **notifies the linked parent** in the app (and as a phone notification).
5. After check-out, the student's **phone GPS** shares the trip home with the parent; the server
   computes the **ETA** and confirms **arrival** within 60 m of the pinned home, then tracking stops.
6. The **SOS** button sends the student's live (or last known) location to the parent at any time.
7. The **teacher dashboard** shows real-time counts of students on campus, late, out and unaccounted,
   and a **Trials** panel with the data for the statistical treatment.

## Architecture

| Part | Technology |
| --- | --- |
| Gate scanner | ESP32-CAM (AI Thinker) + 0.96" I2C OLED + active buzzer + green/red LEDs — `firmware/` |
| Back end | Node.js + Express, running as a Vercel Function (`api/index.js` → `server/`) |
| Database | PostgreSQL (Neon, through the Vercel Marketplace) with the Drizzle ORM (`server/db/schema.js`) |
| Front end | React web app (Vite) with separate student, parent and teacher views (`src/`) |
| Notifications | In-app (refreshes every 5 s) + Web Push to the parent's phone |
| Hosting | Vercel (functions in Singapore, `sin1`) |

```
ESP32-CAM ──HTTPS──▶ /api/attendance/qr/verify ─┐
Student phone ─────▶ /api/student/* (pass, GPS, SOS) ├─▶ Express ─▶ Drizzle ─▶ PostgreSQL
Parent phone  ◀────▶ /api/parent/*  + Web Push       │
Teacher       ◀────▶ /api/teacher/* (status, trials) ┘
```

## Accounts and roles

- **Student** — signs up with email, password, student number (format `2026-0001`) and section.
- **Parent** — signs up *after* the child, with the child's student number and the one-time
  **parent link code** the child makes in their app (Parent section). One parent per student;
  a parent sees only their own child.
- **Teacher** — signs up with the **teacher access code** (`TEACHER_SIGNUP_CODE`, stored in
  `.env.local` and in the Vercel project's environment variables). Teachers see attendance only,
  never locations.

Forgotten password: `vercel env pull .env.production.local --environment=production`, then
`node --env-file=.env.production.local scripts/reset-password.js someone@example.com`
prints a temporary password.

## Scanner rules

| Situation | Result |
| --- | --- |
| First valid scan of the day | Check-in: **On Campus**, or **Late** after the cut-off (default 7:01 AM) |
| Same pass again within the repeat-scan window (default 2 min) | Confirmed, nothing new recorded |
| Next scan after that | **Checked Out** |
| Pass already used for check-in and check-out | Rejected (`USED PASS`) |
| Code older than 3 minutes, or one the app has already replaced | Rejected (`EXPIRED`), nothing recorded |
| Pass from another day | Rejected (`EXPIRED`) |
| Any other QR code | Rejected (`INVALID QR`) |

Teachers can change the late cut-off, the repeat-scan window and the starting ETA speed under
**Settings**. A teacher's phone camera can also scan passes (**Backup scanner**) if the ESP32-CAM is
unavailable; those scans are logged as "teacher phone".

To aim and focus the ESP32-CAM, teachers can open `/teacher/camera` (not linked from the menus). For
5 minutes after each restart the scanner sends its camera picture there, with brightness, sharpness
and how many QR codes it found and read.

## ETA

ETA = remaining road distance ÷ speed.

- Remaining road distance = straight-line distance from the phone to the home pin × 1.3.
- The speed starts at the configured average (default 20 km/h) and moves toward the trip's own
  observed speed (progress so far ÷ time so far) as the trip goes on, fully after 15 minutes,
  limited to 4–60 km/h. The estimate adapts to walking, jeepney or tricycle rides.
- The first estimate is saved as the *predicted arrival*; the *ETA error* is actual arrival minus
  predicted arrival.

A web page can read GPS only while it is open, so the student keeps the app open until home (the
app keeps the screen awake during the trip).

## Data for the statistical treatment

Everything is logged automatically. Teachers see the summary under **Trials** and download CSV files.

| Measure (paper) | Where it comes from |
| --- | --- |
| Scan accuracy (success rate) | Scan log: accepted / rejected (with reason) / errors |
| Scan response (mean, SD) | Scanner round trip per scan (QR read → answer on the OLED), measured on the ESP32 |
| Notification response time (mean) | Event time (scan or GPS) → first arrival on the parent's phone (push receipt or in-app) |
| Cycle success rate | Scan → status update → parent notified |
| ETA accuracy (MAE) | Predicted vs actual arrival for each trip |
| Reliability (MTBF) | Scanner uptime from heartbeats ÷ failures (restarts, Wi-Fi drops, failed requests, server errors) |

`trials.csv` has one row per student per day with the whole cycle side by side (check-in, notified,
response seconds, check-out, ETA, arrival, ETA error).

## Privacy (Data Privacy Act of 2012, RA 10173)

- Consent is asked at sign-up.
- Location is collected only during the trip home (after check-out) and when SOS is pressed, and is
  shown only to the linked parent. Teacher accounts never receive location data.
- GPS points are deleted after 30 days; the trip summary (times, distance, ETA) is kept for the study.
- Scanner camera pictures are sent only for 5 minutes after the scanner starts, only the newest one is
  kept, and only teacher accounts can see it.
- Passwords are stored as scrypt hashes; sessions use an HttpOnly cookie.

## Running locally

```bash
npm install
npm run dev     # web on http://localhost:5173, API on http://localhost:3001
npm test        # end-to-end API tests on a temporary database
npm run lint
```

Locally the API uses a built-in Postgres (PGlite) stored in `.pglite/`, so no database setup is
needed. Secrets for local use are in `.env.local` (see `.env.example`).

## Deploying to Vercel

The project is linked to the Vercel project **campuspulse-acnsths**.

```bash
vercel deploy --prod
```

The build (`npm run vercel-build`) applies the database migrations in `drizzle/` and builds the web app.

Environment variables (Vercel › Project › Settings › Environment Variables):

| Name | Purpose |
| --- | --- |
| `DATABASE_URL` (and the other `PG*` / `POSTGRES_*`) | Added automatically by the Neon integration |
| `DEVICE_API_KEY` | Shared secret the ESP32-CAM sends; same value as in `firmware/.../secrets.h` |
| `TEACHER_SIGNUP_CODE` | Code needed to create a teacher account |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` | Keys for phone (Web Push) notifications |

After changing `server/db/schema.js`, run `npm run db:generate` to create a new migration.
